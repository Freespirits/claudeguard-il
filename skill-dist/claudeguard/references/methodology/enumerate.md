# Enumerate — building the inventory by hand

Completeness is not a feeling. It is achieved by naming a **set**, listing every member of it,
and then applying a rule to every member. There is no other mechanism. A pass that "looked at
the auth code" covers nothing; a pass that lists all 23 routes and dispositions all 23 of them
covers 23 routes.

This file tells you how to build those lists from a repo you can only read — and, more
importantly, **how to know when your list is incomplete and must be declared so.**

Do this before you grade anything. The inventory is the input to `methodology/grade.md` and the
denominator in `methodology/coverage.md`.

---

## 0. Ground rules

**Enumerate first, judge later.** While enumerating, record only what is there. The moment you
start deciding whether a route is "fine", you stop listing and start sampling, and the count
stops being trustworthy.

**Record a location for every subject.** `path/to/file.ts:42`. The user checks your work in
their own editor; a finding without a file:line is an assertion, not evidence.

**Skip the same directories the engine skips**, and say that you did: `node_modules`, `.git`,
`dist`, `build`, `.next`, `out`, `coverage`, `vendor`, `.venv`, `__pycache__`, `.turbo`,
`.cache`, `android/build`, `ios/Pods`. Also skip dotfile directories except `.github`.

**Resolve path aliases before you claim an import goes nowhere.** Read `tsconfig.json` /
`jsconfig.json` → `compilerOptions.paths`. `@/lib/db` is almost always `src/lib/db.ts`. An
unresolved alias silently deletes edges from your reachability reasoning.

## 1. Routes

**The set:** every HTTP entrypoint the deployed app exposes.

Where they live:

| Pattern | Kind |
|---|---|
| `app/**/route.{ts,tsx,js,jsx}`, `src/app/**/route.*` | App Router handler |
| `pages/api/**/*.{ts,js}` | Pages API route |
| `supabase/functions/**`, `netlify/functions/**`, `api/**` | Serverless function |
| `server/**`, Express/Fastify `app.get(...)`, `router.post(...)` | Custom server |

Record per route:

- `file` and the derived **URL path**. `app/api/orders/route.ts` → `/api/orders`;
  `pages/api/orders.ts` → `/api/orders`. Strip `src/`, `app/`, `pages/`, the trailing
  `/route.ts`, and a trailing `/index`. **Route groups `(marketing)` are organisational and do
  not appear in the URL** — drop those segments or you will report a path that does not exist.
- **methods** — exported `GET`/`POST`/`PUT`/`PATCH`/`DELETE` functions, or
  `req.method === '...'` comparisons. If you find none, treat the route as **mutating**: an
  unknown method set is not a safe method set.
- **mutating** — anything other than GET-only.
- **auth signal present?** Any of `getUser`, `getSession`, `auth()`, `requireUser`,
  `requireAuth`, `currentUser`, `verifyToken`, `jwt.verify`, `getServerSession`, `clerkClient`,
  `withApiAuth`, `authenticate`, `isAuthenticated`, `session?.user`, `verifyIdToken`.
  **This is a presence signal, not a verdict** — see LAW 1 and `false-positives.md` FP-11.
- **validation signal present?** `.safeParse(`, `.parse(`, `zod`, `yup`, `joi`, `valibot`,
  `superstruct`, `ajv`.
- **rate-limit signal present?** `ratelimit`, `rateLimit`, `limiter.`, `Ratelimit`, `throttle`.
- **uses the service-role key?** `SERVICE_ROLE` / `service_role` anywhere in the file. This is
  what makes an unauthenticated route a total compromise rather than a scoped one.

**Then read `middleware.ts` / `src/middleware.ts` before you conclude any route is unauthenticated.**
Record whether it contains an auth signal, and record its `matcher`. A route covered by an
authenticating middleware matcher is **not** a "no auth" finding — reporting it is the fastest
way to produce twenty findings on a correctly-built app.

When you interpret a matcher, be **conservative in the direction of under-claiming coverage**:
if you cannot confidently parse the pattern, treat it as *not* covering the route and let the
route become `undeterminable`, rather than asserting a protection you cannot demonstrate.

**Incompleteness triggers:** a custom server that registers routes in a loop or from a config
array; routes generated by a framework plugin; a `[...catchAll]` segment; anything under a
directory you did not read. Declare the set open and say which part you could not close.

## 2. Database tables

**The set:** every table the application can reach. This set has **four independent sources**,
and you must check all four, because the modal vibecoded app has tables in only some of them.

1. **Migrations** — `**/*.sql`, usually `supabase/migrations/`. The only source that can tell
   you the **RLS state**.
2. **Generated Supabase types** — `database.types.ts`, `supabase.types.ts`, `types/supabase.ts`,
   `supabase/types.ts`. Read the keys directly under `Tables:` inside the `public:` block. This
   file is generated **from the live database**, so it is the authoritative *list* — it includes
   tables created in the dashboard that no migration mentions.
3. **ORM schema** — `schema.prisma` (`model X {`) or Drizzle (`pgTable('x', ...)`).
4. **Code references** — `.from('table_name')` calls. A table used in code but present in no
   schema source still counts as an enumerated subject.

Record per table: `name`, where it was `knownFrom` (which of the four), `definedIn` location,
`rlsEnabled`, where RLS was enabled, and its policies (name, command, whether the predicate is
`true`, whether it references `auth.uid()`).

### Trap: read SQL with comments stripped

Before matching anything, mentally blank out `--` line comments, `/* */` blocks, and string
literals. A commented-out line:

```sql
-- alter table public.orders enable row level security;
```

reads as proof that RLS is **on** if you match the raw text. That is a false *negative*: it
hides a P0 behind a checkmark. Same for `create policy` inside a comment.

Dollar-quoted function bodies (`$$ ... $$`) are also "strings" for this purpose — but do not
forget them, because that is where `SECURITY DEFINER` logic lives. Read them separately
(section 6).

### Trap: the schema exists only in the Supabase dashboard

This is the single most common shape in this audience: **no `supabase/migrations/` at all.** The
user clicked "New table" in the dashboard. Consequences:

- The repo contains **zero** evidence of RLS state. Not "RLS is off" — *unknowable*.
- If you enumerate tables only from `.sql` files you will find **zero tables**, and the flagship
  "table has no RLS" rule will produce nothing, while a coverage row implies you checked.
- The partial case is worse: six tables in migrations all pass, and the seventh — added later in
  the dashboard — never appears in your list at all.

What to do:

- Enumerate from generated types and `.from()` calls anyway, so the tables at least appear.
- Mark every table whose RLS state is not proved by a migration as
  **`rlsCertainty: unknown-no-migration`** → disposition `undeterminable`. Never `false`
  (invents a P0), never `true` (hides one).
- Emit **one loud blocking unknown**, not N quiet ones. A user with no migrations needs a single
  instruction, not a wall of identical rows.
- Hand the user this query **verbatim** so they can answer in ten seconds what the repo cannot:

```sql
select c.relname,
       c.relrowsecurity as rls_enabled,
       (select count(*) from pg_policy p where p.polrelid = c.oid) as policies
from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind = 'r'
order by 1;
```

Say plainly, in both languages, that this is the difference between "we did not find a problem"
and "there is no problem".

### Trap: non-literal `.from(x)` behind a generic CRUD helper

```ts
export async function getAll(table: string) {
  return supabase.from(table).select('*')     // which tables? unknowable from here
}
```

A literal `.from('orders')` enumerates. `.from(table)` does not: the set of tables reached
through that helper is computed at runtime. **This must be visible, never a silent skip** — a
silent skip is how you claim complete coverage while blind.

Record each non-literal call site as its own `undeterminable` subject in a `dynamicTableRefs`
set: `` `.from(table)` at lib/db.ts:14 — the tables it reaches cannot be enumerated statically ``.
Then, if you can, list the call sites of the helper as the reviewer's follow-up work.

## 3. Environment variables

**The set:** every name that either appears in code or is declared in an env file.

Read from code:

- `process.env.NAME`
- `process.env['NAME']`
- `import.meta.env.NAME` (Vite)

Read from files: every `.env*` in the repo, including `.env.example`. Record for each name the
file, the line, whether it **has a value**, and whether the file is an `.example`.

Then classify each name on **three independent axes** — keep them separate, because collapsing
them is exactly how the false P0s happened:

**(a) Exposure — does the value reach the browser?**

| Exposure | When | Strength |
|---|---|---|
| `bundler-inlined-public-prefix` | Name starts with `NEXT_PUBLIC_`, `VITE_`, `PUBLIC_`, `EXPO_PUBLIC_`, `REACT_APP_`, `GATSBY_`, `NUXT_PUBLIC_` | **definitive** — the bundler substitutes the value into client output textually |
| `next-config-inlined` | Listed in `next.config` `env:` or `publicRuntimeConfig` | **definitive** — no prefix needed |
| `referenced-in-client-module` | Read in a module reachable from a client entrypoint, **but no public prefix** | **NOT a leak.** See FP-01 |
| `example-only` | Named in `.env.example`, no value, never read by any code | Nothing exists yet. See FP-04 |
| `server-only` | Neither of the above | Structurally cannot reach the browser |

**(b) Secret class — from the name alone (LAW 3 territory).**

- `public-by-design` — `SUPABASE_ANON_KEY`, `SUPABASE_URL`, `FIREBASE_API_KEY`, `FIREBASE_*`,
  `SENTRY_DSN`, `POSTHOG_KEY`, `STRIPE_PUBLISHABLE*`, `PUBLISHABLE_KEY`, `MAPBOX*`,
  `GOOGLE_MAPS*`, `RECAPTCHA_SITE_KEY`, `PUSHER_APP_KEY`, `ALGOLIA_SEARCH_KEY`, `VAPID_PUBLIC`.
  These are **never** a leaked secret. See FP-02.
- `high` — the name alone is near-conclusive: `SERVICE_ROLE`, `*_SECRET`, `SECRET_*`,
  `SECRET_KEY`, `PRIVATE_KEY`, `PASSWORD`, `ACCESS_KEY_ID`, `SECRET_ACCESS_KEY`, `*_TOKEN`,
  `SESSION_KEY`, `ENCRYPTION_KEY`, `SIGNING_KEY`, `WEBHOOK_SECRET`, `DATABASE_URL`, `DB_URL`,
  `CONNECTION_STRING`, `*DSN`; plus named provider keys — `OPENAI|ANTHROPIC|CLAUDE|GEMINI|GROQ|
  MISTRAL|COHERE|REPLICATE|HUGGINGFACE|TOGETHER|PERPLEXITY|DEEPSEEK|XAI|OPENROUTER|ELEVENLABS|
  STRIPE|TWILIO|SENDGRID|RESEND|POSTMARK|CLOUDINARY|AWS|GCP|AZURE` followed by
  `_API_KEY`/`_KEY`/`_SECRET`/`_TOKEN`, with or without a public prefix.
- `weak` — looks credential-ish but is routinely publishable: anything matching `API_KEY`,
  `APIKEY`, `TOKEN`, `CREDENTIAL`, `*_KEY`, `AUTH` that did not match the above.
- `none` — nothing suggests a credential.

**(c) Client reachability — and how strongly.** See section 5.

**Also record env-guard libraries.** If any file calls `createEnv({ server, client, runtimeEnv })`
(t3-env or a lookalike), record it. A `runtimeEnv` block **necessarily names every server
variable**, so a naive reader sees "secrets referenced in a client-imported file" in the one
repo that is doing this correctly. Credit it; never punish it.

**Incompleteness triggers:** variables read via a computed key (`process.env[keyName]`),
variables injected by the host (Vercel/Netlify dashboard) that appear nowhere in the repo,
`.env` files that are gitignored and therefore absent. Say that the set covers only what the
repo declares or reads.

## 4. LLM call sites

**The set:** every file that talks to a model provider.

Signals: `openai`, `anthropic`, `generative-ai`, `@ai-sdk`, `generateText`, `streamText`,
`chat.completions`, `messages.create`, `getGenerativeModel`.

Record per site: file; whether it is client- or server-reachable; `dangerouslyAllowBrowser: true`
(definitive P0 — the SDK's own guard has been switched off); whether a token cap is set
(`max_tokens` / `maxTokens` / `maxOutputTokens`); rate-limit signal; auth signal; whether the
prompt is built by interpolating request data into a template literal; and whether the site
**defines tools** the model may invoke (`tools:`, `tool(`, `function_call`,
`functionDeclarations`, `toolChoice`).

The combination that matters most: **user input reaching a prompt at a site that also defines
tools.** That is prompt injection with a reachable consequence, not a lecture about prompt
injection in general.

**Incompleteness triggers:** a provider called over raw `fetch` to an API URL, a self-hosted
gateway, or an SDK you do not recognise. If the repo pays for tokens somewhere you cannot see,
the rate-limit and cost findings are incomplete — say so.

## 5. The client/server boundary (needed by 3 and 4)

You need this to answer "can the browser see it?". Build it as a two-step reachability walk.

**Client seeds** (a secret referenced here really does ship):
`'use client'` directive in the first ~400 characters; `pages/**` that is not `pages/api/**`;
`src/{main,index,App}.{ts,tsx,js,jsx}` in a Vite/React SPA; in a Vite app, `src/**` that is not
`*.server.*`.

**Server seeds:** `'use server'`; `pages/api/**`; `app/**/route.*`; `middleware.*`;
`*.server.*`; `server/`, `api/`, `functions/`, `netlify/functions/`, `supabase/functions/`,
`scripts/`.

Then walk imports outward from the seeds and record **how strong** each reachability claim is:

- **strong** — the file *is* a client entrypoint, or is imported **directly** by one (one hop,
  not through a barrel).
- **weak** — reached only transitively, or through a re-export barrel.

Only `strong` may drive a P0. `weak` caps at needs-review.

### Trap: re-export barrels

A **barrel** is a module that is mostly `export * from './x'` / `export { y } from './y'` — say,
60% or more of its non-blank lines. `lib/index.ts` is the canonical one.

`import { cn } from '@/lib'` does **not** mean the bundler ships `lib/db.ts` and its service-role
client: tree-shaking drops unused re-exports. Treating a chain through a barrel as strong
evidence **fabricates a P0 on a correct app** — and a wrong P0 makes people rotate keys and
announce breaches. Mark barrel-mediated reachability `weak`, and name the assumption: *"that
tree-shaking does not drop this module from the client bundle."*

### Trap: `import 'server-only'`

If a module contains `import 'server-only'`, importing it from a client component is a **build
error**. The chain therefore cannot exist in a shipping app. Stop the walk at that module — do
not propagate client reachability through it, and do not report anything downstream of it as
client-exposed.

### Trap: monorepo / workspace imports

Turborepo and pnpm workspace scaffolds are common here, and `apps/web` importing `@repo/db` is
the normal shape. If you treat `@repo/db` as a third-party package, **every cross-package edge
disappears** — and reachability silently under-reports in exactly the multi-file repos where
reading the whole graph is supposed to be the advantage.

Do this:

1. Read `package.json` → `workspaces`, and/or `pnpm-workspace.yaml` → `packages:`.
2. For each matching directory, read its `package.json` and map **package name → directory**.
3. Resolve `@repo/db` → `packages/db` (try also `packages/db/src`), and `@repo/db/client` →
   `packages/db/client` or `packages/db/src/client`.
4. A workspace package you **know about** but cannot resolve to a file is a **coverage hole, not
   a third-party dependency**. Record it as an unresolved workspace import and say the graph is
   incomplete there.

## 6. Smaller sets, still enumerated

- **`next.config.*` keys** — `env:`, `publicRuntimeConfig`, `productionBrowserSourceMaps: true`,
  `typescript.ignoreBuildErrors: true`, `eslint.ignoreDuringBuilds: true`, image
  `remotePatterns` with `hostname: '*'`/`'**'`, and whether a `headers()` function exists at all.
  Strip comments first; a commented-out config block is not config.
- **Supabase client construction sites** — every `createServerClient`, `createBrowserClient`,
  `createRouteHandlerClient`, `createServerComponentClient`, `createClientComponentClient`,
  `createMiddlewareClient`, `createPagesBrowserClient`, `createPagesServerClient` (all
  **anon / user-scoped**), plus every plain `createClient(url, KEY)` whose identity depends
  entirely on *which key* the second argument is: `service-role`, `anon-public`, or
  `unknown-key`.
- **SQL functions** — `create [or replace] function`. Record `security definer`,
  `set search_path`, and whether the body references `auth.uid()` / `auth.jwt()`.
- **Artifact classes** — mobile manifests (`AndroidManifest.xml`, `Info.plist`), GitHub workflow
  files, Dockerfiles / compose files / Terraform, and Firebase rules files each get their own set
  (`mobileArtifacts` + `exportedComponents`, `ciWorkflows`, `iacFiles`, `firebaseRules`; what to
  look for is in `checks/`). Any file class you saw and will not grade goes into
  `ungradedSurfaces` as `undeterminable` — see `grade-or-declare.md`. A discovered class that
  appears in no set is the defect that rule exists to kill.

## 7. Declaring the inventory INCOMPLETE

This is the part that matters. An enumeration you cannot close is fine; an enumeration you
*pretend* you closed is a lie the user will act on.

**Declare the set open whenever any of these is true:**

- You did not read every file — on claude.ai this is the default: you saw what was pasted.
  Say so explicitly and name the sets that are therefore partial.
- A directory or file was skipped: over ~1.5 MB, minified, binary, unreadable encoding.
- A non-literal `.from(x)`, a computed `process.env[k]`, or a dynamic `import()` appeared.
- A workspace package could not be resolved to files.
- Reachability for a subject was established only through a barrel.
- No schema source exists (no migrations, no generated types, no Prisma/Drizzle).
- The framework registers routes in a way you cannot statically list.
- A live-tier question (does this header actually get sent? does the anon key actually return
  rows?) cannot be answered from source at all.

**How to declare it.** Not as a caveat at the bottom. As rows in the ledger and as one sentence
in the report body, bilingual (HE + EN — the sentence is user-facing prose; file paths, SQL and
identifiers stay English):

```
Coverage: tables — 7 enumerated, 0 pass, 0 fail, 7 undeterminable.
No migrations exist in this repo, so RLS state cannot be read from source.
Run the query below against your database to settle it.

כיסוי: טבלאות — 7 נמצאו, 7 לא ניתנות לקביעה.
אין קבצי migration במאגר, ולכן לא ניתן לקבוע את מצב ה-RLS מהקוד.
הריצו את השאילתה הבאה מול מסד הנתונים כדי לקבל תשובה.
```

Then hand over the exact query or the exact file to open. An undeterminable row without an
instruction is just an apology; with one it is the most useful line in the report.
